# The voice isolator's MLX engine: how it was ported, and how to update it

`meethook transcribe` isolates the voice in the mic track with Inworld's voice isolator. On macOS
it runs the network on the GPU through MLX; everywhere else (and in a sandboxed `nix build`) it
runs the ONNX graph on the CPU. The MLX engine is about 11x faster through the whole mic stage. This file records where the
MLX code came from, what is different, and the steps to bring it up to date, because the source
it was ported from is a young third-party project that will change.

Code: `crates/meethook-transcribe/src/mlx_isolator.rs` (the network),
`mlx_kernels.rs` (generated Metal kernels), and the engine switch in `voice_isolator.rs`.
Measurements and the CoreML dead end are in the `voice_isolator` module docs.

## Provenance

| What | Where | Pinned at |
|---|---|---|
| The model | Inworld AI, `inworld/voice-isolator` (Apache-2.0), `denoiser.safetensors` | |
| The MLX Swift port we translated | <https://github.com/starkdmi/VoiceIsolatorMLX> (Apache-2.0, Copyright 2026 Dmitry Starkov), version 0.1.0 | commit `3d45405` ("Initial upload"), read 2026-11-20 |
| The converted weights we load | `starkdmi/VoiceIsolator_v1_48K_MLX`, `model_fp16.safetensors` | HF revision `0bf480815ac77bba0429a0aae96859759560f441`, sha256 `ffb1f727...`, 159,659,684 bytes (`VOICE_ISOLATOR_MLX_MODEL` in `models.rs`) |
| MLX bindings | `mlx-rs` 0.34 (crates.io, `oxiglade/mlx-rs`), which builds Apple's MLX through `mlx-sys` | `~0.34` in the workspace `Cargo.toml` |

The Metal kernels are copied verbatim from the Swift package (its `KernelSources.swift`, whose erf
is adapted from MLX, MIT). The network is translated by hand, not generated: Swift to Rust,
operation for operation. Attribution is in the module docs of `mlx_isolator.rs` and
`mlx_kernels.rs`.

## What was ported, and where it went

Only the offline model's forward pass, fp16. In the Swift package's `Sources/VoiceIsolatorMLX/`:

| Swift | Rust (`mlx_isolator.rs` unless noted) |
|---|---|
| `Network.swift` `Linear`, `LayerNorm`, `gelu` | `Linear`, `LayerNorm`, `gelu` |
| `Network.swift` `Attention` | `Attention` (non-causal only) |
| `Network.swift` `MambaAxis` | `Mamba` (no carried state, no streaming history) |
| `Network.swift` `DualPathAttention`, `DualPathMamba`, `Network.backbone` | `Block`, `MlxNetwork::backbone` |
| `Network.swift` `Network.encode` / `decode` | `MlxNetwork::encode` / `decode` |
| `Network.swift` `correctionParts`, `Network.correction` | `MlxNetwork::try_correction` |
| `Network.swift` `ropeTables` | `rope_values` (pure Rust) and `rope_tables` |
| `Config.swift` `bandEdges`, `BandLayout` | `band_edges`, and the index tables built in `MlxNetwork::try_load` |
| `Kernels.swift` `Kernels`, `SeqLayout` | `Kernels`, `launch`, `Layout` |
| `KernelSources.swift` | `mlx_kernels.rs`, generated by `scripts/sync_mlx_kernels.py` |
| `Isolator.swift` `chunkPlan`, `enhance` | `voice_isolator.rs` `plan_windows`, `isolate` (shared with the ONNX engine) |
| `DSP.swift` STFT / iSTFT | `voice_isolator.rs` `Stft` (shared with the ONNX engine) |
| `Weights.swift` `load` | `MlxNetwork::try_load`, reading the already converted file with `Array::load_safetensors` |

## Deliberate differences

- **The engine boundary is the ONNX graph's contract.** The network takes the window's spectrum
  `[1, frames, 1025, 2]` (real, imaginary) and returns the complex correction of the same shape.
  The STFT, inverse STFT, windows and crossfades are `voice_isolator.rs`, once, for both engines.
  The Swift package does the STFT on MLX and owns the windows. This is why the two engines can be
  compared directly, and it is why the last-window alignment fix helped both.
- **No 4096-token chunking** (`Pass`, `alongTime`, `alongBands`). Every window is at most 801
  frames, so one pass fits (about 2 GB peak, with the layer-sized evaluation described below). The Swift package chunks to bound memory for
  arbitrary inputs.
- **Each sequence layer is evaluated before the next is built, a failed window is retried, and a
  span that still fails is left un-isolated.** All three exist because of the GPU watchdog
  described under "Things learned". The first two are in `mlx_isolator.rs`
  (`backbone`, `correction`); the last is in `mic_isolation.rs` (`IsolationReport::failed_batches`).
  Upstream has none of them.
- **No-RoPE head split is its own kernel** (`split_plain`) for the band axis, as upstream, not an
  identity table.
- **The buffer cache is cleared after each window** (`mlx_rs::memory::clear_cache`). MLX keeps freed
  buffers keyed by size; the mic stage sends spans of every length, so without this the cache
  grew past 19 GB on a 30 minute track. Upstream bounds it instead (`--cache-limit-mb`, default
  512).
- **Hardcoded config.** Upstream reads the architecture from the weights file's metadata; here it
  is constants at the top of `mlx_isolator.rs` (width 512, 8 heads, 46 bands, block order, Mamba
  sizes, correction bound 0.5). They match the metadata of the pinned file.
- **Not ported:** the realtime/streaming model and session, 8-bit quantization, bf16/fp32, the
  checkpoint converter, audio I/O and resampling. 8-bit was piloted with the Swift CLI and is
  *slower* than fp16 (46.4 s against 35 s for 129 s of audio), because the quantized layers compute
  in float32; only the download is smaller (92 MB), so it is not worth porting.

## Updating

**Upstream kernel sources changed.** Clone the Swift package, then
`python3 scripts/sync_mlx_kernels.py PATH/TO/KernelSources.swift`. Review the diff in
`mlx_kernels.rs`: a changed kernel usually means `Kernels::new`, a launch grid or a template
argument in `mlx_isolator.rs` must change with it (compare `Kernels.swift`).
`scripts/sync_mlx_kernels.py ... --check` exits 1 when the file is out of date.

**Upstream network changed** (`Network.swift`). Diff it against the table above, change the matching
Rust, and re-run the checks below.

**New weights.** Update `VOICE_ISOLATOR_MLX_MODEL` in `models.rs`: the URL's pinned revision
(`curl -sI https://huggingface.co/<repo>/resolve/main/model_fp16.safetensors` shows
`x-repo-commit`, `x-linked-size` and `x-linked-etag`, which is the sha256). Then confirm the
hardcoded constants still match the file's metadata:

```
python3 -I - <<'EOF'
import json, struct
f = open("model_fp16.safetensors", "rb")
header = json.loads(f.read(struct.unpack("<Q", f.read(8))[0]))
print(json.loads(header["__metadata__"]["config"]), header["__metadata__"]["format_version"])
EOF
```

The loader needs `format_version` 3, `in_pad_multiple` 1 and no quantization; it checks the encoder's
shape and the absence of `.scales` tensors and refuses anything else with a clear error.

**`mlx-rs` or MLX upgrade.** Bump the tilde pin, then build and run the checks. The calls this uses:
`MetalKernel::new` / `apply`, `fast::layer_norm`, `fast::scaled_dot_product_attention`,
`Array::load_safetensors`, `ops::{addmm, concatenate, stack, take_axis, ...}`,
`memory::clear_cache`.

## Checking a change

All need the models; none run in CI (they download weights). From the repo root:

```
cargo test --release -p meethook-transcribe --lib voice_isolator -- --ignored --nocapture
```

runs the parity test: the engine this build uses against the official Python package on
`testdata/voice-isolator/sample_14.wav` (regenerate the reference with
`scripts/voice_isolator_reference.py`). Expected: **75.3 dB for MLX** (floor 70 dB, the Swift port
measures 75.4 dB against the same reference), 125.6 dB for ONNX (floor 90 dB). To compare the two
engines and time them: `cargo run --release --example isolate-voice -p meethook-transcribe
crates/meethook-transcribe/testdata/voice-isolator/sample_14.wav`, and for the whole stage on a real recorder track
`... isolate-voice mic.cleaned.wav --stage --track --minutes 30` (add `--only cpu` for ONNX).
Watch memory with `footprint -p <pid>` (macOS blocks `ps -o rss` for some processes): MLX should
stay near 2.3 GB through the whole stage; a steady climb means the cache is no longer cleared.

## Building

The `mlx` feature of `meethook-transcribe` is on by default and compiles MLX's Metal shaders, so
a macOS build needs Apple's **Metal Toolchain**, which Xcode 26 no longer bundles:

```
xcodebuild -downloadComponent MetalToolchain
```

- **Dev shell (`nix develop`).** The first `xcrun` on `PATH` is nix's stub, which cannot find
  Metal, and `DEVELOPER_DIR` points at the nix SDK, which has no toolchains. The flake puts
  `nix/xcrun-metal-shim.sh` in front: `metal` and `metallib` run from the host Xcode's toolchain,
  everything else is passed through unchanged. Do not set `TOOLCHAINS` globally: it breaks the C++
  compiler detection.
- **CI.** `.github/scripts/ensure-metal-toolchain.sh` installs the toolchain on macOS runners
  before the jobs that build the workspace (`ci.yml` test, clippy, docs; `cd.yml` build).
- **`nix build .#meethook`.** A sandboxed build has no Xcode and cannot compile Metal (nixpkgs
  builds MLX with `MLX_BUILD_METAL=false` for that reason), so the flake builds with
  `--no-default-features` and the package runs the ONNX engine. Release tarballs come from
  `cd.yml`'s native `cargo build` in the dev shell, so they have MLX. `VoiceIsolator::required_model()`
  tells the caller which weights the build needs, so a package without MLX downloads the ONNX
  graph, not the MLX file.
- **Outside nix.** A plain `cargo build` on a Mac with Xcode and the Metal Toolchain works. If it
  fails with `missing Metal Toolchain`, `xcrun -sdk macosx metal --version` is the test; with a
  nix-provided `DEVELOPER_DIR` in the environment, use the shim or unset it for the build.
- **`--no-default-features`** builds the ONNX engine on macOS too.

## Things learned

- CoreML through ONNX Runtime cannot run this graph in any configuration tried (it either fails to
  compile or passes 16 GB within seconds); the MLX kernels are what make it fit. Numbers are in the
  `voice_isolator` module docs.
- The ONNX engine's earlier 46.7 dB against the reference was the zero-padded last window, not
  the model; both engines now use the official window plan.
- macOS can kill a GPU command buffer that runs long while the GPU is also drawing the screen or
  serving another process (`[METAL] Command buffer execution failed: Impacting Interactivity`). It
  happened once in about eight runs of the end-to-end test. The engine evaluates one sequence layer
  at a time to keep buffers short, retries a failed window, and the stage leaves a span that still
  fails un-isolated. It was not possible to provoke on demand, so those mitigations are reasoned,
  not proven against a reproducer.
- A window of any length works (the frame axis is dynamic), so short speech spans are not padded
  to 8 s.
- `mlx-sys` is built by cmake, so a restored `target/` cache can point at nix store paths that no
  longer exist; the CI cache-eviction script handles that for the other native crates the same way.
