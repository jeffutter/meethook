A full-screen, ratatui-based interface for naming voices during enrollment was added as a third implementation of the existing `Interviewer` trait boundary that already separated "what an answerer is handed" from "what a person sees" — never replacing the existing headless, line-based path, which must stay reachable from CI, shell pipelines, and scripted or LLM-driven runs. Which interface a run actually gets follows a fixed priority — an explicit given name always wins outright; otherwise, if either stdin or stdout isn't a real terminal, or a `--plain` flag is set, the plain line-based prompt runs; only when none of those apply does the full-screen interface start — landed and reviewable before the full-screen interface itself existed, specifically so the guarantee that a driven run can never accidentally open a full-screen UI could be verified independent of the UI's own correctness.

The interface itself is split into a fully unit-tested state machine with no terminal I/O, clock, or rendering types in it, and a thin rendering/event-loop shell around it — a stricter bar than the existing line-based path was held to, imposed deliberately because "a few hundred lines of full-screen interaction logic" doesn't get the same pass "about sixty lines of straight-line prompting" earned. Several capabilities needed new library-level design to support a full-screen view rather than being purely presentational: a ranked list of how closely a voice resembles every enrolled speaker (deliberately unthresholded, since a human reading a ranked list is exactly the case the automatic matching threshold is biased against serving well); resolving a typed name against the enrolled set as an explicit three-way outcome — an exact match, a list of near-miss candidates, or a genuinely new name — that never silently guesses between two real people with similar names; and a way to preview exactly what accepting a given name would write to the database before any key commits it, built by dry-running the same code path a real commit uses against cloned state, rather than as a second, parallel implementation of the same rules that could drift from the first.

Answering voices out of the order they're queued in is supported through an explicit "not this one yet" deferral that the session re-offers until a full pass produces no further answers, rather than through batching several answers together and committing them at once — deferral was chosen specifically because it keeps every answer's preview and every safety check honest against the database exactly as it stands at that moment, where batching would let an earlier answer in the same batch go stale by the time a later one in the same batch is evaluated; real multi-voice batching remains a deliberately separate, still-open question. Audio playback runs as a background spawn/poll/stop cycle rather than blocking the interface for a clip's duration, and extends to individual transcript lines rather than only the single longest representative clip per voice, since recognizing a voice usually comes from one specific remembered sentence rather than however happened to be the longest thing they said. A background, non-blocking scan surfaces which other people's stored references a given name currently applies to — reusing the exact same scan the existing `speakers` command already runs rather than a second implementation — since a name like "Ivan" identifies a person to whoever typed it, not necessarily to whoever is looking at a list of candidates weeks later.

The existing safety rule that refuses an answer if it would silently take a stored name away from someone else can now be explicitly overridden — but only for that specific refusal, never for the separate, categorical "these are provably different people" veto — and the override is carried on the answer itself rather than decided purely inside the full-screen interface's own state, specifically so a scripted driver or the plain line prompt, which never pass through that interface's code at all, still see the same override behavior rather than hitting a guard the full-screen interface alone knew how to bypass.

## Considered options

- Replacing the headless CLI with the full-screen interface — rejected outright; CI, pipelines, and scripted runs must keep working unattended.
- Deciding UI-vs-headless selection inside the interface itself rather than before it starts — would make the "a driven run can never open a full-screen UI" guarantee untestable independent of the UI.
- A second, parallel implementation of "what would this answer write" instead of dry-running the real commit path — risks the preview drifting out of sync with what actually gets written.
- Real batching of several answers committed together, instead of deferral — deliberately left open; batching risks an earlier answer in a batch going stale before a later one in the same batch commits.
- Letting the full-screen interface decide refusal overrides on its own — would let the line prompt or a scripted driver hit a guard the full-screen interface alone knew how to get past.
