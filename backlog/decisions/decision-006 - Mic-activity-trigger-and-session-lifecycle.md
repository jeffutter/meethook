Recording starts and stops automatically from microphone activity rather than any explicit user action, using an event-driven CoreAudio listener rather than polling, with an immediate start and a short debounced stop so a brief mid-call gap doesn't split one meeting into two sessions. The original design used the device-level "is running somewhere" property as the sole signal, validated against real hardware showing it correctly distinguishes a mute (no device event) from a full call end (the property flips false). That signal turned out to be insufficient once meethook holds its own audio tap: opening the recorder's own input pins the property true for the rest of the session, so it can only serve as a fast start trigger, not a stop signal, and had to be replaced by a predicate derived from CoreAudio's per-process audio objects that explicitly excludes meethook's own process.

That replacement predicate needed its own corrections, discovered only on real hardware. Apple's ScreenCaptureKit system-audio helper process, `replayd`, showed up in the per-process list after recording started and pinned "someone else is capturing" true for the rest of the session even after the real meeting app had left — fixed by excluding that helper's bundle ID unconditionally, since a time-window heuristic tried first proved too fragile to the helper's actual timing. A second meethook instance left running from an earlier crash was found holding another instance recording for 41 minutes, because CoreAudio reports no bundle ID for a plain Rust binary — fixed by excluding a second instance by its resolved executable path instead, asymmetrically: a pid whose path can't be read is excluded on the assumption it might be us, but an unreadable path from a definitely-foreign pid is not, so a real meeting app can't be silently filtered out. And a hardware run showed the stop-edge notification can be read microseconds too early and simply lost, with no way to make a single read of the predicate "win" that race — the fix was not a better read but a cheap periodic recheck of the whole predicate every two seconds while a session is live, trading a few seconds of stop latency for a guaranteed recovery from any single missed edge. A parallel per-process CoreAudio listener that was expected to serve as a second chance at every edge never fired once across several hours of hardware testing and was removed rather than kept as a documented-but-unreliable fallback.

A default input device change mid-session (unplugging a headset, for instance) finalizes the current session and opens a new one, rather than rebuilding the audio tap into the same files, because the alignment math downstream measures one acoustic lag per session and the WAV format itself can't hold two sample rates in one file. Separately, a stalled or dead microphone engine — from a device reconfiguration, an exclusive grab by another app, sleep, or any other cause — is detected from whether the track's own delivered-frame counter has advanced recently, checked on the same recheck tick, rather than from any specific CoreAudio notification; this covers every cause structurally, since notifications only cover the causes someone thought to subscribe to, and needs no dedicated sleep/wake handling because a sleep that kills the engine is just another instance of the same stall.

## Considered options

- The original device-level "is running somewhere" signal alone — self-triggers once meethook holds its own audio tap.
- A fixed post-start time window to exclude `replayd`'s notification — measured too short relative to the helper's actual timing.
- A pidfile/advisory-lock single-instance guard instead of excluding a second process by executable path — judged the better long-term fix, but out of scope for a targeted bug fix; not built.
- A settle-and-reread after any notification that produces no edge — still can't recover an edge for which no notification arrives at all.
- Watching `AVAudioEngineConfigurationChangeNotification` for a stalled engine — covers only two of several real causes and needs new, sandbox-untestable observer plumbing that a delivered-frame counter doesn't.
